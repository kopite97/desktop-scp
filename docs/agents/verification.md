# 검증 지침

적용: 검증 선택·실행·증거·완료 판정.
탐색: [PLAN 관리](plan-management.md), [실행 하네스](harness.md), [Godot 도구](godot-tools.md).

## 범위 선택

| 변경 | 기본 확인 |
| --- | --- |
| 문서·상태 | 링크·메타데이터·목록 일치·문서 길이·내용 검토 |
| 문서 검사기 | 정상 fixture 및 잘못된 문서/상태를 거부하는 회귀 테스트 |
| 게임 규칙 | 공통 명령과 실제 상태를 사용하는 로직 시나리오 |
| 삭제 후 소멸 애니메이션 | 즉시 입력/예약/생존 수 해제, 중복 회수 방지, 표시 수명·캐시 유지/해제, 봉쇄/복귀/앱 종료 및 별도 수신기의 실제 클릭 투과 |
| 화면·입력 | 실제 Godot 표시·입력·상태 연결 |
| 조명·재질 연결 | [Art 조명 검증 계약](../../Art/docs/agents/lighting.md)의 실제 렌더링·다중 창·입력·비용 비교 |
| OS 연결 | 실제 Windows에서 해당 좌표·창·클릭 투과·수명 검증 |

- 변경 영향에 맞는 최소 충분한 검증을 선택한다. 새 변경·실패·남은 우려가 없으면 반복하거나 확대하지 않는다.
- 정적 검사·컴파일·실행·내보내기·성능 측정은 서로 다른 결과다.
- 일반 C# 컴파일과 필요한 기능 테스트는 실행 승인된 구현 범위에 포함할 수 있다.
- 배포용 내보내기와 고부하 측정은 PLAN에 목적·대상·시간·산출물 및 요청 범위를 명시한다.
- 다른 프로젝트의 빌드 승인 규칙을 자동 이식하지 않는다. 이미 받은 사용자 지시는 같은 범위에서 유효하다.
- 시스템 지표 반응 검증은 모의 입력을 우선한다. 실제 CPU 부하를 높이는 테스트와 구분한다.

## 판정

1. 환경·코드/설정·실행 대상·명령을 확인한다.
2. 실행 결과·종료 코드·테스트 수·실패·건너뜀과 관련 로그를 함께 확인한다.
3. 대상 테스트가 0개이거나 결과 파일이 없으면 통과로 처리하지 않는다.
4. 증거가 해당 실행에서 생성되었는지 확인한다. 이전 로그를 새 증거로 사용하지 않는다.
5. 미실행·실패·환경 문제·통과를 구분하고 제한과 다음 행동을 남긴다.
6. 실패를 없애기 위해 테스트를 완화했다면 제품 문제 해결로 보고하지 않는다.

## Windows 확인

- 모의 창·모의 커서로 확인한 규칙과 실제 OS에서 관찰한 결과를 구분한다.
- 배율·모니터 배치·작업 영역·대상 창 상태를 증거에 기록한다.
- 화면 캡처만으로 클릭 투과를 판정하지 않는다. 뒤쪽 테스트 창의 입력 수신도 관찰한다.
- 화면 표시·게임 논리·입력 차단·OS 효과 중단을 각각 확인한다.
- 성능 수치는 측정 조건과 실제 측정값을 함께 남긴다. 미측정을 성능 무회귀로 표현하지 않는다.

## 증거와 문서 검사

- 실행 결과는 PLAN에 요약하고 상세 자료는 실행별 evidence에 보관한다.
- 최소 기록은 환경·대상·명령/조작·기대 결과·실제 결과·판정·미검증 범위다.
- 필요하지 않은 화면·로그 전문을 계속 수집하지 않는다.
- 문서 검사기는 구조적 오류를 찾는다. 승인 근거의 진위·완료 증거의 의미·제품 동작은 사람이 읽어 판정한다.
- 현재 링크 검사는 Markdown 인라인 링크의 로컬 파일 존재를 확인한다. 제목 앵커·웹 주소·참조형 링크는 검사하지 않는다.
- 검사기 자체 테스트의 통과와 전체 프로젝트 문서 검사의 통과를 따로 기록한다.
- 필수 기준이 남으면 PLAN을 completed로 전환하지 않는다.
