# 아키텍처 지침

적용: 상태 소유·엔진 의존성·Windows 연결·공통 처리 설계.
탐색: [실행 하네스](harness.md), [Windows 연동](windows-integration.md), [기술 결정](../decisions/README.md).

## 책임 경계

| 책임 | 담당 내용 |
| --- | --- |
| 게임 규칙·상태 | SCP 행동·스트레스·가짜 오브젝트·봉쇄와 복귀 상태 |
| Godot 표현·입력 | 화면 표시·애니메이션·UI·사용자 조작 변환 |
| Windows 연결 | 모니터·창·입력 활동·시스템 지표 취득과 외부 효과 실행 |
| 검증 하네스 | 초기 조건·환경 입력·진행·관찰·실행 증거 |

이는 설계 기준이며 현재 코드가 존재한다는 뜻은 아니다. 클래스·프로젝트 분할은 필요한 시점에 정한다.

## 상태와 공통 경로

- 게임 상태마다 소유자를 정한다. 화면과 하네스가 별도 상태 원본을 유지하지 않는다.
- 사용자 조작과 검증 명령은 같은 규칙 검사·상태 변경 경로를 사용한다.
- 표현 객체의 표시·삭제만으로 논리 개체의 존재와 상태를 판정하지 않는다.
- 입력·환경 관찰, 게임 판정, 외부 효과 요청을 구분한다.
- 외부 효과는 실행 직전에 봉쇄·옵션·대상 유효성을 확인한다. 이전 프레임의 허용만으로 실행하지 않는다.
- 이벤트 구독·타이머·OS 핸들·입력 감시의 소유자와 종료·재시작 시 정리 책임을 정한다.
- 제품 코드가 테스트 도구나 검증 전용 데이터에 의존하지 않게 한다.
- 조명·시간대 표현과 아트 리소스의 연결은 [Art 조명 계약](../../Art/docs/agents/lighting.md)을 참조한다. 여러 창의 조명 상태 소유자·시간 입력·검증 경로를 개발 PLAN에 명시한다.

## 추상화 판단

- 실제 환경과 모의 환경을 교체해야 하는 입력·시간·외부 효과 경계부터 작게 분리한다.
- 모든 클래스에 인터페이스를 만들거나 DI 프레임워크를 기본 도입하지 않는다.
- 값 전달·작은 함수·구체 객체로 독립 검증이 가능하면 그 방법을 우선한다.
- 비슷한 코드 모양보다 같은 규칙·변경 이유인지 확인한다.
- 현재 단계에 필요한 구조만 구현한다. 미요구 원격 서비스·완전한 결정성·범용 엔진을 선행 조건으로 만들지 않는다.

## 결정과 검증

- 여러 기능에 영향을 주거나 교체 비용이 큰 선택은 TECH로 기록한다.
- 후보와 실제 적용을 구분하고 적용 코드·설정 및 검증 PLAN을 연결한다.
- 초기화·종료·반복 실행·봉쇄/해제·환경 변경 중 관계가 유지되는지 변경 영향에 맞춰 검증한다.
- 기술 선택으로 미정 제품 수치나 동작을 확정하지 않는다.
