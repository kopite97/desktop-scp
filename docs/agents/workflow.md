# 작업 절차

적용: 작업의 시작·재개·종료와 문서 변경.
탐색: [루트 MAP](../../AGENTS.md), [PLAN 관리](../plans/plan.md).

## 시작과 재개

1. 사용자 요청과 기존 파일 변경을 확인한다. 기존 작업을 덮어쓰지 않는다.
2. 저장소 루트에서 `node scripts/validate-agent-docs.mjs`를 실행한다.
3. 개발 PLAN 작업이면 docs/plans의 유일한 active PLAN을 읽는다. 아트 제작은 [Art 작업 절차](../../Art/docs/agents/workflow.md)에서 해당 ART를 확인한다.
4. [기획 MAP](../game-design/README.md)과 [로드맵](../game-design/roadmap.md)에서 관련 기준을 찾는다.
5. 루트 MAP에서 해당 작업의 세부 지침을 읽는다. 링크된 지침이 자동 로드되었다고 가정하지 않는다.

검사기를 실행할 수 없으면 PLAN 메타데이터와 목록을 직접 확인하고 실행 불가 이유를 남긴다.
검사 오류가 있으면 원인을 확인한다. 상태가 불명확한 채로 기능 구현을 진행하지 않는다.
active 0개는 정상 대기 상태다. 사용자 요청에 따른 조사·문서 관리·후보 작성은 가능하다.
PLAN 실행과 전환은 [PLAN 관리](../plans/plan.md)를 따른다.

## 기록의 원본

| 위치 | 기록할 내용 |
| --- | --- |
| 기획 원본과 docs/game-design | 제품 동작·범위·미정 항목·단계별 완료 기준 |
| docs/agents | 작업 방법·필수 참조·운영 규칙 |
| docs/plans | 개발 PLAN 관리 규칙, 개발·Godot 통합 범위·진행·다음 행동·실제 검증 결과 |
| Art/docs/plans | [아트 PLAN 관리](../../Art/docs/plans/plan.md), 제작·리비전·검수 진행 |
| docs/plans/evidence | 실행별 로그·결과·필요한 화면 |
| docs/decisions | 영향이 큰 기술 선택·이유·대안·적용 위치 |

PLAN이나 기술 결정으로 제품 기획을 조용히 변경하지 않는다.
위임된 구현 상세는 범위 안에서 판단하고 근거를 남긴다. 같은 승인을 반복 요청하지 않는다.
새 제품 동작이나 범위 변경이 필요하면 미정 사항으로 기록하고 사용자 의사를 확인한다.

## 진행 갱신과 종료

1. 의미 있는 작업·검증 후 PLAN의 체크리스트·현재 상황·다음 행동을 갱신한다.
2. [검증 지침](verification.md)에 따라 실제 결과와 증거를 기록한다.
3. 작은 구현 선택은 PLAN에, 여러 기능에 영향을 주는 선택은 [기술 결정](../decisions/README.md)에 기록한다.
4. PLAN 상태 전환 시 목록을 갱신한다. 단계 완료 기준을 충족한 경우에만 로드맵을 갱신한다.
5. 문서·상태 변경 후 검사기를 다시 실행하고 결과·미검증 범위·남은 작업을 보고한다.

## 문서 유지

- 루트 AGENTS.md는 탐색 MAP만 담고 100줄 이내로 유지한다. 절차·명령·상태 규칙은 하위 지침에 둔다.
- docs/agents의 각 Markdown과 docs/plans/plan.md는 150줄 이내로 유지한다. 한 규칙의 원본은 한 곳에 둔다.
- 주제가 달라지거나 길어지면 분리하고 읽기 조건과 링크를 MAP에 추가한다.
- 긴 문장을 한 줄로 합쳐 줄 제한을 우회하지 않는다.
- 미구현 경로·예시 명령은 예정임을 표시하고 존재하는 파일처럼 링크하지 않는다.
- 설치 버전·명령·검증 결과는 확인한 사실만 기록한다.
- 과거 증거는 당시 사실로 보존한다. 현재 지침과 다른 과거 상태를 현재 규칙으로 복사하지 않는다.
