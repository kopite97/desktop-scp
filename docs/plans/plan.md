# PLAN 관리 지침

PLAN은 검증 가능한 작업 단위의 목표·범위·현재 진행·다음 행동을 기록한다.
탐색: [루트 MAP](../../AGENTS.md), [작업 절차](../agents/workflow.md), [PLAN 목록](README.md), [로드맵](../game-design/roadmap.md).
이 문서가 개발 PLAN 관리 규칙의 원본이다. 개별 작업 PLAN이나 현재 작업 상태를 담는 파일이 아니다.

적용 범위는 프로젝트 docs/plans의 개발·Godot 통합 작업이다.
아트 원본 제작은 [Art PLAN 관리](../../Art/docs/plans/plan.md)에 따라 Art/docs/plans의 ART-NNN으로 관리한다.
개발 PLAN과 ART는 각각 active 최대 1개이며, 각각 명시적으로 승인받으면 동시에 진행할 수 있다.
한쪽의 실행 승인이 다른 쪽의 제작·구현 승인을 대신하지 않는다.

## 현재 작업 찾기

- 실제 PLAN은 이 디렉터리 바로 아래의 `PLAN-NNN-topic.md`다. README·plan.md·템플릿·evidence는 PLAN이 아니다.
- 필수 메타데이터는 `id`, `type`, `status`, `title`, `updated`다. 날짜는 `YYYY-MM-DD`를 사용한다.
- 타입과 상태의 원본은 각 PLAN의 메타데이터다. 목록의 type·status는 원본을 보여주는 요약이다.
- 루트에서 `node scripts/validate-agent-docs.mjs`로 문서 상태와 active 수를 확인한다.
- active는 최대 1개다. 0개는 정상 대기 상태이며 2개 이상은 오류다.
- 실행 가능한 PLAN은 사용자 승인을 받은 유일한 active PLAN이다. 승인 근거·범위·선행 조건도 함께 확인한다.
- active가 0개이면 PLAN 실행을 시작하지 않는다. 사용자 요청에 따른 조사·문서 관리·후보 작성은 [작업 절차](../agents/workflow.md)에 따라 진행할 수 있다.
- active가 2개 이상이면 PLAN 실행을 멈추고 사용자 요청·전환 이력을 근거로 상태를 복구한다.

## PLAN 목록 README의 역할

- [README](README.md)는 제목과 PLAN 링크·작업 단위·type·status 목록 표만 유지한다.
- 진행 설명·검증 수치·증거·막힌 점·후속 제안은 개별 PLAN 본문에 기록한다.
- PLAN 생성·타입 변경·상태 전환 시 목록을 같은 변경에서 갱신한다.
- 로드맵·기획 MAP에 관련 상태 표기가 있으면 함께 대조·갱신한다. 단계 완료는 실제 검증 결과로 별도 판정한다.
- 검사기 통과만으로 기획 단계나 제품 기능이 완료되었다고 간주하지 않는다.

## 타입과 완료 판정

| type | 주목적 | 완료 판정 |
| --- | --- | --- |
| development | 기능·기반 시스템·환경·문서·저장소 등 일반 개발 | 범위의 작업과 필수 기능·검증을 충족하고 증거 기록 |
| art | Godot의 정식 아트 적용·교체 등 통합 변경 | 자기 범위의 필수 아트 적용·기술 검증·사용자 시각 확인 완료 |

- development는 정식 아트 미수령·교체·시각 확인 대기만으로 완료를 막지 않는다. 임시 표현으로도 필요한 기능은 실제 검증해야 한다.
- art는 자기 범위의 필수 리소스·참조 연결·검증·시각 확인을 완료 조건에 명시한다. 다른 작업의 아트까지 기다리는 조건으로 확대하지 않는다.
- 기능 개발 중 Sprite가 필요해졌다는 이유만으로 type을 art로 바꾸거나 별도 아트 PLAN을 자동 생성하지 않는다.
- 타입 변경으로 미구현·실패한 검증·필수 아트 적용을 우회하지 않는다.
- 완료된 development PLAN을 남은 아트 때문에 재활성화하지 않는다. 후속 작업은 별도 범위로 관리하고 과거 완료·증거를 보존한다.
- 미실행·건너뜀·환경 문제를 통과로 기록하지 않는다. 필수 완료 기준이 남으면 completed로 바꾸지 않는다.

## 상태

| status | 의미 |
| --- | --- |
| proposed | 후보 작업. 구현에 착수하지 않음 |
| active | 사용자 승인을 받은 현재 유일한 실행 대상 |
| completed | 범위와 필수 검증을 완료하고 증거를 남김 |
| rejected | 취소·미채택. 이유와 남은 변경을 기록함 |
| on hold | 보류. 중단 지점·이유·재개 조건을 기록함 |

위 값의 소문자·공백을 그대로 사용한다. blocked·done·paused 등 새 상태를 임의로 추가하지 않는다.
같은 범위의 독립 작업이 가능하면 active를 유지하면서 막힌 점을 본문에 기록할 수 있다.

## 생성과 활성화 승인

- **사용자의 명시적 승인 없이 status를 active로 전환해서는 안 된다.** proposed → active와 on hold → active 모두에 적용한다.
- 모든 새 PLAN은 proposed로 작성한다. 생성과 동시에 active로 지정하지 않는다.
- 사용자가 해당 PLAN의 실행·활성화·재개를 명시적으로 승인한 경우에만 선행 조건을 확인한 뒤 active로 전환한다.
- PLAN 작성·검토 요청, 기획 승인, 로드맵 순서, 선행 PLAN 완료, 검사 통과, 에이전트 판단은 해당 PLAN 실행 승인으로 간주하지 않는다.
- active 0개를 채우기 위해 임의 활성화하지 않는다. 완료·보류·취소 이후 다음 PLAN도 별도 실행 승인 근거가 있어야 한다.
- 기존 명시적 승인은 철회·범위 변경이 없는 한 같은 대상·범위에서 유효하다. 이미 받은 승인을 반복 요청하지 않는다.
- 여러 PLAN 실행을 명시적으로 승인받았다면 대상·순서·범위를 기록하고 하나씩 활성화한다. 승인을 받지 않은 후속 PLAN까지 확대하지 않는다.
- 승인 대상이나 범위가 불명확하면 active로 전환하지 않고 확인한다.
- 활성화·재개 시 승인 날짜, 사용자 지시의 인용 또는 정확한 요약, 대상 PLAN·범위를 상태 전환 기록에 남긴다.
- active는 작업 대상 선택이다. 설치·배포·제품 범위 확장 등 별도 행위의 권한을 자동으로 부여하지 않는다.
- 문서 검사기는 상태·목록 일치를 확인할 뿐 사용자 승인의 진위를 판정하지 않는다. 실행 전 실제 요청과 기록을 대조한다.

## 상태 전환과 기록

| 전환 | 조건·기록 |
| --- | --- |
| proposed → active | 해당 PLAN 실행에 대한 명시적 승인과 선행 조건 충족 |
| active → completed | 범위의 작업·완료 기준·필수 검증 충족, 실행 증거 연결 |
| active → on hold | 중단 지점·이유·재개 조건 기록 |
| on hold → active | 재개 조건 충족과 해당 재개를 허용하는 명시적 승인 근거 |
| proposed / active / on hold → rejected | 미채택·취소 근거와 남은 변경 기록 |

전환마다 날짜·이전 상태·새 상태·이유·요청/검증 근거를 본문에 기록한다.
완료하지 않은 일을 상태 정리를 위해 completed로 바꾸지 않는다. completed·rejected 작업의 새 기능은 새 PLAN으로 작성한다.

## 템플릿과 작성 내용

1. [_template.md](_template.md)를 복사하고 고유한 PLAN ID와 proposed 상태로 작성한다.
2. 관찰 가능한 목표, 포함·제외 범위, 작업 요청·위임 근거를 적는다.
3. 기준 기획·관련 지침·로드맵 단계·선행 PLAN을 연결한다.
4. 결과물 위치·작업 목록·완료 기준·검증 방법을 구체화한다. 전체 개발을 하나의 거대한 PLAN으로 만들지 않는다.
5. 현재 상황·다음 행동·막힌 점·실제 검증 결과는 해당 PLAN 한 곳에서 갱신한다.
6. 중요한 기술 선택은 [기술 결정](../decisions/README.md)에, 작은 구현 선택은 PLAN에 남긴다.

아트 통합 작업은 같은 템플릿에 디자인 의도·사용처·규격·리비전·수령/적용 상태와 제작 ART 링크를 보완한다.
애니메이션은 방향·동작·프레임·재생 조건을, UI는 화면·상태·입력 영역을, 정적 아트는 점유·연결·가려짐을 명시한다.
미정·제안·확정값과 원본 시각 확인·제품 화면 확인을 구분한다. 기존 승인값을 예시로 덮어쓰지 않는다.
제작 원본과 제출본은 [Art 구조](../../Art/docs/agents/project-structure.md)를 따른다. 참고 프로젝트의 독립 요청 예외를 자동 도입하지 않는다.

## 결과물 저장 위치

- 산출물별 기준 루트·디렉터리·파일명·확장자와 생성/변경/재사용/예정 여부를 지정한다. 해당 없음은 사유를 적는다.
- 멀리 있는 proposed 후보는 문서·검증 산출물을 먼저 지정하고 제품 파일 상세를 활성화 전 보완 항목으로 남길 수 있다. 실행 전에는 구체 경로를 확정한다.
- 아트는 작업 원본·리비전·수령·제품 적용·검수 자료의 경로를 대응시킨다. 원본을 불필요하게 복제하지 않는다.
- 실행 증거는 `docs/plans/evidence/PLAN-NNN/run-NNN/`에 두고 README·결과·로그·필요한 화면의 파일명을 지정한다.
- run-001·r001 등 최초 번호와 증가 규칙을 정하고 이전 실행·리비전 증거를 덮어쓰지 않는다.
- 미생성 경로는 코드 표기로 예정임을 명시한다. 경로 지정만으로 빈 폴더·가상 결과물을 만들지 않는다.
- 생성 후 실제 링크·적용 리비전·위치를 기록한다. 선택 자료가 없거나 기존 자료를 재사용하면 이유·원본 위치를 남긴다.

## 검증과 마감

- [검증 지침](../agents/verification.md)에 따라 변경 영향에 맞는 검증을 고르고 실제 환경·방법·결과·증거·미검증 한계를 기록한다.
- 일반 C# 컴파일·에디터 실행·배포용 내보내기·고부하 측정을 구분한다. 실행 범위는 이 프로젝트의 지침과 사용자 요청을 따른다.
- 도구 호출 성공·문서 작성·설치·설계 승인과 실제 기능 구현·검증 완료를 구분한다.
- 문서·상태 변경 후 검사기를 실행하고 원본·목록·관련 기획 표기의 일치를 확인한다.
- 이전 PLAN 완료는 다음 PLAN의 실행 승인이나 검증 완료를 뜻하지 않는다.
